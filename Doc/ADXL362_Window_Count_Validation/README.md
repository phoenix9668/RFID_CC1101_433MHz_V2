# ADXL362 方案二：长时间逐窗计数验证

日期：2026-10-27。结论：**当前测试板保存的最近 16 个连续完整窗口，六类计数合计每窗均为 1200，通过本轮长时间逐窗计数验证。**

16 个窗口对应 320 分钟（5 小时 20 分钟）的统计区间，超过此前 4 小时 20 分钟长跑目标。该结论适用于当前测试板及记录中的运行条件，不代表行为识别准确率、原基站接收或生产功耗已验收。

完整设备备份、探针信息及原始 UART 保存在被忽略的 `.local/`，不随本报告公开。可审阅的脱敏结果为 [window-counts.csv](window-counts.csv) 和 [results.json](results.json)。

## 完整性和连续性

1. EEPROM 为 2048 字节，16 条历史记录和 30 条检查点记录共 46 条均通过提交标记、格式、类型、范围和 CRC 校验。
2. 采用已有 `Tools/inspect-eeprom.cjs` 解码，再用独立 Python 解码器重新核对，全部记录字段一致。
3. 16 条历史记录序号从 9476 至 9791，相邻差值均为 21，与每分钟检查点及每窗口封存记录的写入节奏一致；历史槽按模 12、物理日志槽按模 16 连续轮转。
4. 全部历史记录的复位计数为 82、窗口进度为 1200 秒，六类计数总和为 1200。最近 12 条覆盖 12 个不同历史槽，总和为 14400。
5. 最新记录是未封存的检查点：进度 1080 秒，六类计数为 `[1079, 0, 0, 0, 0, 1]`，合计 1080。本轮将其排除在完整窗口门槛之外。
6. EEPROM 双读相同，设备身份及旧区逐字节未变，选项字节未变；Flash 回读与普通 Diagnostics 二进制一致。输入文件与 CSV 的 SHA-256 保存在 `results.json`，原始文件留在私密备份中。

### 与早先长跑日志的关系

早先保存的约 4.5 小时 UART 日志结束后，板卡仍继续运行；本次读取的 16 条历史记录属于同一复位计数 82 运行段中更晚的区间。不能把这些记录逐条配到那份旧日志的 14 次边界上。

本轮因此直接以 EEPROM 封存记录核对逐窗总计；此前的 UART/逻辑分析仪证据继续用于支持 RTC 窗口节奏及采集链路。历史记录没有独立的绝对时间戳，320 分钟由 16 个连续的 1200 秒窗口确定。

### 计数口径

`history_count()` 保持原规则：类别 1–6 进入对应计数，其他标签（包括启动阶段的 0）归入“其他”。上一轮报告曾把原始导出残窗的 656 个输出扣除 16 个预热标签后写为 640，这是“有效标签数”与“实际历史计数总和”的混淆；该残窗实际历史总和应为 656。相关本地分析报告已纠正。

本次结论来自保存的六类计数直接求和，不是从 UART 分类行数推算。

## 可复核步骤与验收范围

对私密备份执行：

```text
node Tools/inspect-eeprom.cjs <EEPROM备份.bin> <同一设备旧EEPROM备份.bin>
```

按序号从旧到新排列 `kind=1` 的历史记录，核对各记录的 `elapsed`、`reset`、六项 `counts`、槽位连续性和总和，并与本目录 CSV 对照。完整复核输出保留在 `.local/window-count-20261027/`。

本项可以确认：在本次板卡运行条件下，当前重采样与统计链路连续 16 个完整窗口没有发生总计少于或多于 1200 的情况。

本项仍不涵盖：行为类别识别准确率、运动输入下的全部情况、异常/掉电后的缺失统计、原基站实际收包，以及生产功耗。读取所需的已授权 UR 复位结束了该连续运行段，随后固件恢复运行。
